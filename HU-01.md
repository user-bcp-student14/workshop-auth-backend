## Contexto

Como consumidor del servicio de autenticacion, necesito recibir un token
firmado con identidad, rol y vigencia explicitos para verificarlo antes de
aceptarlo. Esta formulacion describe el comportamiento existente; no autoriza
cambios ni acredita la integracion con consumidores externos.

Segun [ENDPOINTS.md](docs/ENDPOINTS.md), POST /auth/login devuelve en un
login valido HTTP 200 con token, expiresIn, user y debug. El token es un
JWT firmado mediante RS256 usando SmallRye JWT y una clave privada RSA
externa de al menos 2048 bits, no HMAC ni un secreto compartido predeterminado.

El emisor establece sub, role, iss, aud, iat y exp.
expiresIn es 3600 segundos y coincide exactamente con exp - iat.
client es opcional, se ignora y no se incorpora al token; exigirlo o validarlo
seria un cambio de contrato fuera de este alcance.

La clave se obtiene mediante AUTH_TOKEN_PRIVATE_KEY_PATH; emisor y audiencia
mediante AUTH_TOKEN_ISSUER y AUTH_TOKEN_AUDIENCE. No se configura
AUTH_TOKEN_SECRET. JWT esta firmado, no cifrado; el consumidor debe verificar
firma, expiracion, emisor y audiencia. Este backend no tiene una ruta
consumidora protegida que permita probar un rechazo HTTP por token vencido.

- Documentar los claims existentes sin agregar client ni requisitos nuevos,
  conforme a [TokenService.java:50](src/main/java/com/bcp/workshop/auth/TokenService.java#L50).
- Medir la duracion con exp - iat, no exp - now: esta ultima cantidad es la
  vigencia restante y disminuye con el tiempo. No inventar una tolerancia.
- Conservar el estado Resuelto de los antecedentes. La coordinacion externa
  mencionada en H-03 no se convierte en un hallazgo Pendiente.
- No modificar codigo, pruebas, configuracion ni el contrato de endpoints.
